# WebDAV Website Engine Gate

Use this gate whenever the user asks to publish, deploy, or make live a site generated by an RDF/SHACL/Jinja2 pipeline (e.g. `sites/openlink/rdf/build.py`).

## Required Interpretation

- The content is **already rendered** before this skill runs. Nothing here re-derives HTML from RDF at request time.
- Publishing means: WebDAV-PUT the generated static files, then map a route to that DAV collection with a static-file `VHOST_DEFINE` (`is_dav=>1`, `def_page=>'index.html'`). No VSP execution, no live SPARQL query, no XSLT skin wrap.
- A local `generated/` folder that has never been WebDAV-published is not "live." Do not describe it as deployed.

## Why not render live (like `weblog-from-webdav` or `osdi-inclusion-engine`)?

Both of those skills render on every request: `weblog-from-webdav` enumerates a WebDAV collection and assembles HTML inline in a bespoke `index.vsp`; `osdi-inclusion-engine` wraps WebDAV-sourced HTML in a shared XSLT skin at request time. Neither model fits here — the content isn't per-file posts to enumerate, and it isn't raw HTML needing a shared skin, it's already the exact bytes to serve, produced by a SHACL-gated pipeline that already enforces the site's content contract (see `rdf-content-mode.md`). Re-deriving those same bytes from a live SPARQL query inside VSP on every request would be new, higher-risk engineering that duplicates what the pipeline already does, for no observable difference to a visitor.

If this ever needs to change — e.g. content should update without a rebuild step — the extension point is documented in `opal-tool-mode.md`, not a silent scope change here.

## Prior-Work Lookup

Before writing SQL or running a publish, search memory or local prior work for:

- `validate_generated_weblog_bundle`
- `VHOST_DEFINE`
- `DAV_RES_UPLOAD_STRSES_INT`
- `website-from-webdav`
- `WS.WS.SYS_DAV_RES`

Carry forward these known fixes (inherited from `weblog-from-webdav`, applicable here wherever `isql`/WebDAV mechanics overlap):

- Avoid `$1`, `$2`, and similar replacement tokens in SQL loaded through `isql`.
- A raw served `<?vsp ... ?>` string in the browser means the route mapping is wrong or VSP execution failed — not applicable to this skill's own static routes, but relevant if debugging a route that was previously VSP-mapped and needs converting to static.
- Delete a prior conflicting `VHOST_DEFINE` for the same host/path before redefining it.

## Required Bundle

For a generated, not-yet-deployed website bundle, include:

- `generated/*.html` — the pipeline's static output.
- `assets/` — `site.css`, `theme.js`, and any other static assets the pages reference, with paths matching what's linked in the HTML.
- `deploy-website-route.sql` — path-substituted for the real target DAV collection and public route, containing `VHOST_DEFINE(..., is_dav=>1, def_page=>'index.html', ...)` and a verification `SELECT` against `WS.WS.SYS_DAV_RES`.
- README or run notes, outside the skill package, describing the target and how to run the deploy SQL and publish script.

## Completion Rule

Do not claim a website publish request is complete until either:

- the live route has been fetched and verified to match the local `generated/` output, or
- the complete deployable bundle passes `scripts/validate_generated_website_bundle.py` and the response clearly states live publication still requires authenticated WebDAV/`isql` access.
